# Porting FAEST's hardware accelerators (AES, GF(2), Keccak) to CVA6

Companion to [FAEST.md](FAEST.md). That document covers running FAEST's
*software* reference implementation on bare-metal CVA6. This one covers
porting the *hardware accelerators* for FAEST's three hot primitives
(AES-128 forward-encrypt, GF(2^128)/GF(2^384-by-128) multiply-reduce, and the
Keccak-f[1600] permutation) — previously built for a different SoC
(`cwrash`'s `pug_rv32` core) — into CVA6's full RV64 SoC, and standalone
software tests proving each one's correctness and speedup before wiring them
into FAEST's own sign/verify code (deferred, not done here).

The 12 `tests/FAEST_*` directories are read-only references for this work —
nothing in them was touched.

## 1. Scope: what's new here vs. what already existed

`keccak_ip/` (AXI-mapped Keccak-f[1600] permutation core, `tests/keccak64/`)
already existed in this repo and was the template for everything below —
studied first, then mirrored exactly for the two new peripherals:

- **`aes_ip/`** (new): AES-128 forward-encrypt-only core, ported from
  `cwrash/rtl/aes_enc128_core.v` (itself a trimmed secworks/aes core — no
  decrypt, no 192/256-bit keys, since FAEST never uses either).
- **`gf2_ip/`** (new): GF(2^128) and GF(2^384)-by-GF(2^128) multiply-reduce
  core, ported from `cwrash/rtl/gf2_mul_core.v`.

Both new peripherals reuse Keccak's exact integration pattern end to end:
plain AXI-mapped MMIO (not a CVXIF custom instruction), register map
generated by lowRISC OpenTitan's `reggen` tool from a `.hjson` spec, software
driver as raw `volatile uint64_t *` MMIO with poll-based completion — no new
architectural pattern was invented.

## 2. SoC wiring

Three places, matching Keccak's own wiring exactly:

1. `corev_apu/tb/ariane_soc_pkg.sv` — added `Aes`/`Gf2` to the
   `axi_slaves_t` enum, `AesBase = 64'h6000_0000` /
   `Gf2Base = 64'h7000_0000` (`AesLength`/`Gf2Length = 64'h1000` each).
2. `corev_apu/tb/ariane_testharness.sv` — `aes_axi_top`/`gf2_axi_top`
   instantiated right after the existing `i_keccak_slv`, plus two new
   `addr_map` entries.
3. **`core/Flist.cva6`** (not the root `Makefile`) — this is the file that
   actually registers RTL sources for Verilator. The root `Makefile`'s
   `src`/`ariane_pkg` variables do **not** list `keccak_ip` either — easy to
   miss; grepping the `Makefile` for "keccak" returns nothing. First attempt
   added the new files to the `Makefile`'s `src` list instead, which caused
   `%Warning-MODDUP: Duplicate declaration of module` (Keccak's files were
   already pulled in via `Flist.cva6`) plus a Verilator internal fault.
   Correct fix: insert the new RTL file list into `Flist.cva6` right after
   Keccak's existing block, reusing its already-present shared
   `prim_subreg`/`axi_to_reg`/`axi_pkg` dependency lines.

`corev_apu/tb/ariane_xilinx.sv` (the FPGA top-level) was **not** touched —
simulation-first, real-hardware wiring is future work.

## 3. Register maps (`reggen`)

`python3 corev_apu/register_interface/vendor/lowrisc_opentitan/util/regtool.py`
generates `<name>_reg_pkg.sv`/`<name>_reg_top.sv` (SystemVerilog) and
`<name>_axi.h` (C register offsets) from each `.hjson` spec.

- **`aes_ip/aes.hjson`**: `KEY`/`BLOCK`/`RESULT` (each a 2×64-bit multireg,
  word 0 = bytes[0:7] big-endian/MSB-first, word 1 = bytes[8:15] —
  reproduces `aes_enc128_core`'s native `[127:0]` convention with zero extra
  byte-swapping), `CTRL` (`INIT`/`NEXT`/`CTR_INC` bits, sw-set/sw-clear),
  `STATUS` (`READY`/`VALID`, hw-driven).
- **`gf2_ip/gf2.hjson`**: `LHS128` (2×64), `LHS384` (6×64), `RHS` (2×64,
  shared by both widths), `RES128`/`RES384` (read-only), `CTRL`
  (`NEXT`/`MODE384`), `STATUS`. Each register is one `uint64_t` limb
  directly (word 0 = low limb) — simpler than AES's convention since there's
  no pre-existing core byte-order to match.

Unlike `cwrash`'s pug_rv32 MMIO wrappers (where control bits self-clear the
cycle after being consumed), `reggen`'s register file holds
software-written bits at a level until software explicitly clears them.
Both new wrappers (`aes_axi_top.sv`, `gf2_axi_top.sv`) use the same
edge-detect-pulse trick `keccak_axi_top.sv` already established
(`*_old` shadow register + `current & ~old`) to turn that level into a
one-cycle pulse for the underlying core's `init`/`next` input.

## 4. The bug: stale `RESULT` reads, and why it wasn't a race

Both `AES128-opt` and `GF2-opt` initially failed their KAT/cross-check with
the *same* symptom: the value read back from a multi-word `RESULT` register
immediately after the `STATUS` poll loop confirmed `READY` was sometimes
stale — reading the *previous* completed operation's value instead of the
current one. `RESULT[1]` (AES) / later words (GF2) were consistently correct;
only the first word read was affected.

### 4.1 What it wasn't

Exhaustive RTL tracing (both `aes_enc128_core.v`'s and `aes_encipher_block.v`'s
FSMs, cycle by cycle) confirmed:

- `RESULT`'s hardware write-enable (`.de`) is driven directly by the same
  `core_valid`/`valid128`/`valid384` wire for every word, asserted on the
  identical clock edge as `READY` — no differential delay between words at
  the RTL level.
- The underlying AES core (`aes_encipher_block.v`) updates all four
  32-bit words of its result register **simultaneously**, on the same edge
  `ready` asserts — verified by tracing `block_w0_we` through `block_w3_we`,
  all gated by the same `FINAL_UPDATE` branch.
- Reordering the software driver to read `RESULT` *before* clearing `CTRL`
  (removing a write-then-immediate-read pattern) had **zero** effect —
  confirmed via disassembly that the reorder actually compiled as intended.
- Adding spacer reads of `STATUS` between the poll loop and the `RESULT`
  read had **zero** effect either.
- Keccak's own driver (`tests/keccak64/keccak_axi.c`) has the exact same
  "clear control bit, then immediately read the first data register"
  shape and works fine, ruling out that pattern in general.

None of these are consistent with a simple bus-spacing or instruction-
ordering race.

### 4.2 What it was

Debug tracing (reading `RESULT` repeatedly, both inside and immediately
after the driver call) showed the *same wrong value* returned consistently
across several back-to-back reads before flipping to the correct one — and
critically, **how many reads it took to settle varied by context**: a
single, isolated call needed one extra read; a call inside a CTR-mode chain
(more preceding bus traffic) needed three or four. This rules out a fixed
pipeline depth and points to some variable-depth buffering in the
`axi_to_reg`/register-file read path that this investigation did not fully
root-cause at the signal level — but the *symptom* (bounded, read-count-based
staleness, not time-based) is fully characterized and reproducible.

Two fix attempts followed from this:

1. **"Read until two consecutive reads agree"** (a standard debounce
   pattern) — plausible-looking but wrong here: since the *stale* value
   itself stays consistent across multiple immediate re-reads, this
   approach declares the stale value "stable" and returns it immediately,
   reproducing the exact original bug.
2. **Unconditional, generous fixed-count discard reads** (the actual fix) —
   `_aes_read_stable()`/`_gf2_read_stable()` in `aes_hal.h`/`gf2_hal.h`
   discard a fixed number of reads (8 for AES, 32 for GF(2) — GF(2)'s
   6-word `RES384` multireg needed a larger margin than AES's 2-word
   `RESULT` to reliably clear) before trusting the value. Crude, but
   directly targets the confirmed symptom and is verified working across
   every test case below, including the CTR-mode chain and both stress
   tests.

This is the one piece of this port that's a **workaround, not a root-cause
fix** — worth revisiting with a waveform trace of `axi_to_reg` if it recurs
on a future peripheral, but out of scope to chase further here given every
test now passes reliably.

## 5. Software drivers

`aes_ip/sw/aes_hal.h` / `gf2_ip/sw/gf2_hal.h` — same raw-MMIO-pointer,
poll-based shape as `keccak_axi.c`, adapted for 64-bit registers and (AES
only) the big-endian word packing above. AES additionally implements
CTR-mode auto-increment (`CTR_INC` control bit + hardware write-back to
`BLOCK[0]`, ported from `cwrash/rtl/aes_mmio.v`'s byte-reversed-32-bit
increment logic, now operating on the top 32 bits of a 64-bit register
instead of a whole 32-bit one) so a block chain only needs one `BLOCK` write
for the first block, not one per block.

## 6. Standalone tests and results

Each primitive gets a software-only baseline (`tests/<NAME>`) and a
hardware-accelerated counterpart (`tests/<NAME>-opt`), each self-contained
(own copies of `aes.c`/`fields.c`/`cpu.c`/etc. plus the `faest_defines.h`
family, following this repo's established `tests/` convention — no shared
source tree). Both halves of each pair print `[CLK] <cycles>` via
`read_csr(mcycle)` so the two runs' logs give a direct cycle-count
comparison.

| Directory | What it tests | Result |
|---|---|---|
| `AES128` | sw AES-128 KAT + 8-block CTR chain | `*** SUCCESS ***`, 1,805,920 cycles |
| `AES128-opt` | hw KAT, hw/sw cross-check, hw CTR chain, 5-iter key+CTR stress (sw cross-checked) | `*** SUCCESS ***`, all bit-exact |
| `GF2` | sw `bf128_mul`/`bf384_mul_128_inplace` timing | `*** SUCCESS ***` |
| `GF2-opt` | hw identities (`x*0`, `x*1`), 100-call timing + sw cross-check, 50-iter stress (both widths) | `*** SUCCESS ***`, all bit-exact |
| `KECCAK` | sw Keccak-f[1600] KAT (`tests/keccak64/keccak_noopt.c`, copied verbatim) | `*** SUCCESS ***` |
| `KECCAK-opt` | hw KAT via the pre-existing `keccak_axi_top` (`keccak_axi.c`, copied verbatim) | `*** SUCCESS ***` |

`AES128-opt`'s combined stress test defaults to a small iteration count
(`AES128_OPT_STRESS_ITERS`, default 5, override via `-D`) — CVA6's full RV64
SoC simulates substantially slower per cycle in Verilator than `cwrash`'s
simpler pug_rv32 core, and each stress iteration also computes a full
software AES reference for the cross-check (~229,045 cycles/block measured
in `AES128`'s own KAT), so the same iteration count that's cheap on
`cwrash` is expensive here. Scale this down further (or up, with patience)
for any new stress test on this SoC rather than assuming `cwrash`'s
parameters port directly.

## 7. What's deliberately not done here

- **Wiring the accelerators into FAEST's own `sign()`/`verify()`** (analogous
  to `cwrash`'s `faest-opt` tree) — explicitly deferred; these tests only
  prove the IPs work standalone.
- **FPGA wiring** (`ariane_xilinx.sv`) — simulation-only for now.
- **Root-causing the `RESULT`-read staleness** at the `axi_to_reg`/waveform
  level (see §4.2) — worked around, not explained.
